NLink 是 NFrp 在标准 frp 线协议之上定义的扩展层，用于承载标准协议没有位置表达的能力。它与 v1、v2 处于同一连接之上：不改变标准帧的字段、顺序与语义，也不要求对端实现它。

:::callout 状态：自 v0.7.4 起提供，默认关闭
全部能力已实现，并由 `server/tests/nlink_e2e.rs` 的 16 条端到端用例逐项覆盖。
服务端与客户端都必须显式配置 `[nlink] enable = true` 才会启用；未启用时行为与 0.6.x 一致。
:::

## 适用范围

NLink 只解决一类问题：需求本身成立，但标准 frp 协议里没有承载它的位置。典型例子是连接迁移——它要求传输层持有独立的连接标识，而标准 frp 在 TCP/TLS 之上叠加 yamux，这个位置并不存在。

因此 NLink 的边界是固定的：

- 不修改标准帧的任何字段含义；
- 不改变标准握手的报文形状；
- 任一侧未声明能力时，自动回退到标准行为；
- 关闭时为零开销，编译产物中不包含相关代码。

## 版本识别

服务端在同一端口上区分四种握手，只依赖首字节：

| 首字节 | 判定 | 依据 |
|---|---|---|
| `0x4E`（`N`） | **NLink** | 魔术字 `NFRPLNK1` |
| `0x46`（`F`） | **v2** | 魔术字 `FRP\x00\x02\r\n` |
| `0x16` | **v1 + TLS** | TLS ClientHello 的首字节 |
| 其它 | **v1 明文** | 按 `[1 字节类型][8 字节大端长度][JSON]` 解析 |

这三个常量互不重叠：v1 的 JSON 以 `{` 开头，v2 以 `F` 开头，NLink 以 `N` 开头。识别过程不包含任何启发式判断。

探测固定预读 **8 字节**（`max(NLink 魔术字, v2 魔术字)`）。早期实现按 v2 魔术字长度（7）填充后再切片到 8 字节比较，一个只发 7 字节便停止的客户端即可触发越界 panic；该问题已修复，并由回归测试 `首帧不足时_detect_version_报错而不是_panic` 覆盖。

## 握手与能力协商

能力声明附加在第一条标准消息之前，协商结果随本就存在的 `LoginResp` 返回，全程不增加往返：

```text
frpc                                             frps
 │                                                │
 ├─ [8]  NFRPLNK1      魔术字                     │
 ├─ [1]  ver = 1       扩展版本                   │
 ├─ [8]  caps          能力位图（大端 u64）        │
 ├─ [16] session_id    进程级连接标识              │
 ├─ [8]  trace_id      端到端追踪                  │
 ├─ 标准 v1/v2 握手 ────────────────────────────▶ │
 │                                                ├─ 解析 preamble
 │                                                ├─ 协商结果 =
 │                                                │   编译期实现 ∩ 对端声明
 │                             ◀───────────────── ┤    ∩ 运行期允许
 │  LoginResp { _nlink: { caps, session, ... } }   │
 │                                                │
 ├─ 后续扩展帧（与标准消息共用同一条流与密文）      │
```

协商结果是本次连接的单一定义，中途不再改变。未知能力位一律忽略，这是向前兼容的前提。

## 扩展帧格式

扩展帧使用版本化 TLV，长度自描述，不认识的内容可安全跳过：

```text
u8   version    扩展帧版本（当前 1）
u8   kind       帧种类
u16  flags      保留，必须为 0
TLV*            每项：u16 tag + u32 len + len 字节载荷
```

承载位置：

- v2：专用帧类型 `0x4E`；
- v1：专用消息类型字节 `0x7F`。

官方实现到 v0.71.0 为止未使用这两个值（官方 v1 的类型字节均为可打印 ASCII），不存在编号冲突。

对方不认识的 `kind` 或 `tag` 必须跳过而非报错。若报错，向前兼容即不成立。

## 能力与承载方式

| 能力 | 承载 | 说明 |
|---|---|---|
| 原生 QUIC 传输与连接迁移 | 独立 ALPN `nfrp-nlink` | 与标准 frp 的 `nfrp-frp` 分桶，同一 UDP 端口可并存 |
| 多路复用 | QUIC 流 | 一条 QUIC 连接承载多条隧道，不受 TCP 队头阻塞影响 |
| 断线续传 | `session_id` + 一次性令牌 + 服务端保留表 | 保留 `resume_ttl` 秒（默认 30），恢复监听器、端口、vhost 与 visitor 本体 |
| 零信任身份 | `NewWorkConn._nlink` 令牌 | 格式 `v1.<exp>.<hmac>`，绑定 `run_id + user + 过期时间` |
| 细粒度限流 | 桥接层令牌桶 | 按「用户 × 代理」共享令牌桶，支持突发；低速率时自动缩小中继块大小 |
| 端口敲门 | 数据面 33 字节序列 | 端口默认对外不可见，验证通过后按来源 IP 临时放行 |
| 批量工作连接 | `BatchReq` 帧 | 一条帧换取 N 条连接，省去逐条 `StartWorkConn` 的往返 |
| 端到端 trace | `trace_id` | 控制连接与数据面共享同一个标识 |

XTCP 的混合版本直连策略，以及与官方 frp 双向兼容的边界用例，也已一并落地，见下方兼容性矩阵。

## 断线续传

### 会话保留

续传保留的是「会话身份 + 监听器 + 端口 + vhost + visitor」，而不是一条名单。重连成功的判定依据是 `session_id` 与服务端签发的一次性令牌同时有效。

### 代理对账

客户端在断线期间可能修改配置。续传成功后，它必须上报「最终仍在的代理」，服务端据此回收未被提及的条目。该帧为 `ResumeCommit`，代理名通过 `TAG_DETAIL` 以换行分隔承载。

### 自动分片

单帧上限为 8192 字节。代理数量较多时名单无法装入一帧，0.7.2 之前的实现只能拒绝发送并记录日志，使「删除代理立即回收」静默降级为 10 秒宽限期。

当前实现由客户端自动分片：每片携带 `TAG_CHUNK`（片序号）与 `TAG_CHUNKS`（总片数），服务端收齐后才结算。

- 仅有一片时不携带分片标记，线上格式与 0.7.1 完全一致；
- 切片按代理名边界进行，不会切断单个名字；
- 乱序到达可正确重组，重复到达不重复计入，新一轮分片会重置旧状态。

### 上限

| 限制 | 值 | 说明 |
|---|---|---|
| 名单总字节 | 8 MiB | 按每个代理名 40 字节计约 20 万个，远超单机实例的实际承载量 |
| 分片数 | 由字节预算推导（约 1100 片） | `TAG_CHUNKS` 为 u16，不会溢出 |

两个上限均为防御性设计：没有它们，客户端可以持续发送分片使服务端持续分配内存，或声明一个巨大的总片数而永不发完。超出预算时服务端拒绝并记录 warn，不影响会话本身。

## 续传的认证边界

续传必须出示**服务端签发的一次性令牌**，仅持有 `session_id` 不足以完成续传。

令牌格式为 `r1.<exp>.<nonce>.<sig>`，使用 HMAC-SHA256，绑定 `session + user + client_id + 过期时间 + 随机 nonce`。随机 nonce 使同一会话重复签发的令牌互不相同。令牌登记在待用表中，**消费即作废**；校验与删除在同一步完成，避免拆成两步产生竞态。

令牌在登录成功时随 `ResumeResp` 下发。断线瞬间控制连接已不存在，无法再发送任何内容，因此必须提前给出。

即便如此仍有一个边界需要使用者判断：当 `transport.tls.force = false`（默认值）时，链路上的观察者可以窃取令牌并抢先消费。真实客户端随后会续传失败并告警——该行为可检测，但无法阻止。

处置方式：

- 服务端启用续传但未强制 TLS 时，启动阶段输出告警；
- 本文档记录该边界；
- **生产环境应开启 `transport.tls.force = true`**，使令牌本身处于加密通道内。

## 启用方式

```toml
# frps
[nlink]
enable = true
# features = ["quic", "resume", "trace"]   # 留空 = 仅协商、不启用具体能力
quic_listen = "0.0.0.0:7000"               # 留空 = 不监听 QUIC
resume_ttl = 30                            # 续传保留时长（秒）
```

```toml
# frpc
[nlink]
enable = true
resume = true      # 断线后用同一 connection id 续传
quic = true        # 经 QUIC 连接服务端（需服务端配置 quic_listen）
```

官方 frpc / frps 不识别 preamble，会把首字节当作 v1 消息头而报错。客户端捕获该失败后自动回退标准模式并仅重试一次，同时记录一条 warn 日志，隧道继续工作。

## P2P 打洞：NatHole 的六种组合

服务端按官方 `pkg/nathole/{classify,analysis}.go` 实现完整的行为选择，mode 0~4 全部在列，并非只支持 EasyNAT 的 mode 0。

判定依据是双方 NAT 特征的三个计数：`easyCount`、`hardCount`、`portsChangedRegularCount`。

| 条件 | 首选 mode | 含义 |
|---|---|---|
| 双方 EasyNAT | mode 0 | 映射稳定，直接对发 |
| 一方 HardNAT，端口规律变化 | mode 1 | 预测端口范围并扫描 |
| 一方 HardNAT，端口不规律 | mode 2 | TTL 控制 + 多轮重试 |
| 双方 HardNAT，均规律 | mode 3 | 双向预测 + 随机监听端口 |
| 双方 HardNAT，一方规律 | mode 4 | 单侧预测 + 随机监听端口 |
| 双方 HardNAT，均不规律 | mode 0（分数 1） | 成功率最低，仍按 mode 0 尝试 |

每张行为表按历史成功率排序：续传与重试时优先选择此前成功过的 mode 与 index，成功后分数 +2（上限 10），由客户端通过 `NatHoleReport` 回报。

随行为表一同下发的参数包括 `portsRangeNumber`、`portsRandomNumber`、`listenRandomPorts`、`ttl`、`sendDelayMs`、`readTimeoutMs`，以及全部 STUN 候选地址 `candidateAddrs`。

这些是协议层能力，能否打洞成功最终取决于两端 NAT 设备的实际行为。HardNAT 场景失败时按 `fallbackTo` 回退中继，这是设计内的降级路径，不是缺陷。

## 与官方 frp 的兼容性矩阵

| 功能 | NFrp × NFrp | NFrp × 官方 frp | 官方 × 官方 |
|---|---|---|---|
| QUIC 传输 / 连接迁移 | 支持 | 回退 TCP | 不支持 |
| 断线续传 | 支持 | 重连重建 | 不支持 |
| 零信任身份 | 支持 | 不启用（令牌不出现） | 不支持 |
| 细粒度限流 | 支持 | 不启用 | 不支持 |
| 批量工作连接 | 支持 | 逐条建立 | 不支持 |
| 端口敲门 | 支持 | 不支持 | 不支持 |
| 端到端 trace | 支持 | 不启用 | 不支持 |
| XTCP 混合版本直连 | 支持 | 需显式策略 | 官方行为 |

与官方 frp 的全部交互均落在「不启用」，不影响连通性。唯一需要特殊处理的是 preamble：官方 frps 会将其视为 v1 消息头并报错，客户端捕获后回退标准模式并重试一次。

## 设计约束

以下五条为 NLink 的硬约束，不满足即不合入。它们是该扩展能够被安全启用的前提。

### 1. 握手期能力协商

双方都必须声明，任一侧缺失即自动回退标准 frp 行为。协商结果决定本次连接的全部行为，中途不再改变。能力以位图加版本号表示，未知位一律忽略。

### 2. 版本化 TLV 与独立命名空间

扩展帧位于独立命名空间，绝不改变标准帧语义。标准帧的字段、顺序与含义一律不动。对方不认识的 TLV 必须跳过而非报错；帧长度自描述，因此跳过是安全操作。

### 3. 两层开关，关闭即零开销

编译期 `nlink` feature（默认开启）与运行期 `[nlink] enable`（默认 false）同时存在。

以 `--no-default-features` 编译时，`LoginResp` 与 `NewWorkConn` 中的 `_nlink` 键**不存在**，报文与 0.6.x 逐字节一致。这一点经实测验证：此时 `cargo tree --no-default-features` 中不含 nlink。

### 4. 双栈共存

同一端口可识别两种握手，判定仅依赖首字节：`NFRPLNK1`、`FRP\0\x02\r\n` 与 `{` 三者互不重叠。扩展握手失败时自动回退，用户无感知。

### 5. 可测试性

兼容性矩阵的每一行都有对应的端到端用例。NLink 相关用例共 16 条，覆盖续传、身份、敲门、限流、QUIC、门控与旧客户端回退。矩阵本身也有测试校验：用例名对不上即判 CI 失败。

## 明确不做

| 设想 | 不做的原因 |
|---|---|
| 修改标准帧的字段含义 | 破坏与官方实现的兼容，违反约束 2 |
| 让扩展默认开启 | 风险不可控，违反约束 3 |
| 在 yamux 之上模拟连接迁移 | 语义错误：迁移必须发生在传输层，模拟实现无法解决问题 |
| 把鉴权从连接级改为逐帧 | 对不支持的对端产生不兼容，应作为可选扩展而非默认行为 |
| 自定义压缩或加密算法 | `useCompression` 与 `useEncryption` 已与官方逐字节对齐，更换算法只会破坏互通 |
