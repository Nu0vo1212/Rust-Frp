NFrp は [fatedier/frp](https://github.com/fatedier/frp) の Rust 再実装です。
**公式の wire protocol v1 と v2 の両方に完全対応**しており、公式の `frps` /
`frpc`（v0.71.0 で実測）とそのまま相互接続できます。サードパーティの frp
サービスが配布する設定もそのまま使えます。

デフォルトは **v1** で、公式 frp のデフォルトと同じです。そのため、
公式クライアント / サーバーは**設定を一切変更せずに**接続できます。

メモリ使用量は小さく、サーバーの常駐メモリは約 3.5 MB です（同じ負荷で
Go 版 frps は 28.8〜31.8 MB）。単一バイナリで、実行時依存はありません。

さらにオプションの拡張レイヤー **NLink v1**（QUIC トランスポートと接続
マイグレーション、セッション再開、ゼロトラスト認証、細粒度レート制限、
ポートノッキング）があります。**デフォルトでは無効**で、双方のネゴシエーション
で有効化され、完全に元へ戻せます。公式 frp への影響はゼロです。詳細は
[NLink v1](#nlink-v1-ネゴシエーションで有効化する拡張レイヤーデフォルトは無効)
を参照してください。

> **完全なドキュメント**: <https://nu0vo1212.github.io/Rust-Frp/>
> インストール、すべての設定キー、8 種類のプロキシ、v1 / v2 の wire protocol、
> ACL / RBAC、監査ログ、HTTP API、セキュリティ修正履歴を収録しています。
> ソースは [`docs/`](docs/) にあり、ローカルでは
> `python -m http.server -d docs 8899` で確認できます。
>
> **品質とリリース**: [QUALITY.md](QUALITY.md) — テスト分布、CI マトリクス、
> 依存関係セキュリティの実際の範囲、リリースゲート、手動チェックリスト。

## インストール

### 方法 1: crates.io（Rust ユーザーに推奨）

3 つのクレートはすべて公開済みです。プロトコルライブラリだけに依存し、
**トンネルサーバーを動かさない**使い方もできます。

```bash
# 実行ファイルを 2 つインストール
cargo install nfrp-server nfrp-client
```

```toml
# あるいは: プロトコル / 設定 / 暗号だけをライブラリとして使う
[dependencies]
nfrp-common = "0.7"
```

| クレート | 用途 | リンク |
|---|---|---|
| **nfrp-common** | プロトコル、設定、暗号、ACL/RBAC、ログ、トランスポート抽象 | [crates.io](https://crates.io/crates/nfrp-common) · [docs.rs](https://docs.rs/nfrp-common) |
| **nfrp-server** | サーバー実行ファイル（公式 `frps` 相当） | [crates.io](https://crates.io/crates/nfrp-server) |
| **nfrp-client** | クライアント実行ファイル（公式 `frpc` 相当） | [crates.io](https://crates.io/crates/nfrp-client) |

> **バージョン番号について**: crates.io のバージョンとこのページの
> Release のバージョンは**独立**しています。たとえば Release が `v0.7.1`
> でも crates.io は `0.7.2` のことがあります。crates.io は同じバージョン
> 番号の再公開を許さないため、README の修正だけでもバージョンを上げる
> 必要があるからです。**コードの挙動は Release を基準**にしてください。
> `cargo install` は常にそのクレートの最新公開版を取得します。
>
> ★ **`cargo install` で得たバイナリは、同じバージョンの Release 内の
> バイナリと同じビルドではありません。** `0.6.6` を例にすると、crates.io の
> 0.6.6 は Release より前に作られ、その後に数か所変更してから `v0.6.6` を
> タグ付けしました（バージョン番号は既に使われていたため再公開できません）。
> したがって **`cargo install nfrp-server@0.6.6` と Release パッケージ内の
> `frps` は挙動が異なる可能性があります**。再現可能で issue に引用できる
> 成果物が必要なら[方法 2: バイナリをダウンロード](#方法-2-バイナリをダウンロード)
> を使ってください。以降のバージョンでは、リリース手順を「まず crates.io に
> 公開し、**同じビルド**で Release をパッケージする」に固定しています。

## 機能

### プロキシ種別

8 種類で、公式 frp の一覧と完全に一致します。

| 種別 | 説明 |
|---|---|
| `tcp` | 最も一般的なポート転送 |
| `udp` | UDP 転送。各プロキシは作業接続 1 本を使い、セッションは訪問元アドレスで区別 |
| `http` | ドメインによるルーティング。`locations` プレフィックス、Basic 認証、Host 書き換え、カスタム要求 / 応答ヘッダーに対応 |
| `https` | ClientHello の SNI だけを覗いてルーティング。TLS は終端せず、証明書は内部サービスが保持 |
| `tcpmux` | HTTP CONNECT の多重化。複数プロキシが 1 つのサーバーポートを共有し、`routeByHTTPUser` で 2 段目のルーティングが可能 |
| `stcp` | プライベートトンネル。サーバーは公開ポートを開かず、`secret_key` と `allow_users` 許可リストで保護 |
| `sudp` | stcp と同じ認証方式でデータプレーンが UDP。こちらも公開ポートを使わない |
| `xtcp` | UDP ホールパンチングと QUIC / KCP の直接接続。データはサーバーを経由しない。失敗時は自動でリレーに戻る。v0.5.8 以降、P2P ハンドシェイクには 2 段階の検証がある（プロバイダーが**派生した応答シークレット**を返し、サーバーがランデブー HELLO を制御接続の送信元 IP に束縛） |

### トランスポート

- frp v1 / v2 の二重 wire protocol。デフォルトは v1 で、`transport.wireProtocol = "v2"` で v2 を有効化
- QUIC トランスポート（`transport_protocol = "quic"`）: 1-RTT ハンドシェイク、ストリーム単位の多重化
- 劣悪回線向けの KCP: xtcp の直接接続チャネルとしても、独立したトランスポート（`kcp_bind_port`）としても使用可能
- yamux 多重化（`transport.tcpMux`）。制御接続と作業接続が 1 本の TCP を共有
- TLS（`transport.tls`）。公式のカスタム先頭バイト偽装を含む。サーバーは自己署名証明書を自動生成し、`certFile` / `keyFile` で差し替え可能。`trustedCaFile` でクライアント証明書（mTLS）を有効化。クライアントは `certFile` / `keyFile` で自身の身元を提示できる
- WebSocket / WSS（`websocket = true`）。同一ポート上でパスにより自動判別し、HTTP のみ許可するファイアウォールを通過できる
- Proxy Protocol v1 / v2。実際のクライアント IP を Nginx / HAProxy / バックエンドへ伝達

### クライアントプラグイン

公式の 9 種類をすべて実装しています: `http_proxy` / `socks5` /
`static_file` / `unix_domain_socket` / `http2http` / `http2https` /
`https2http` / `https2https` / `tls2raw`。frpc 単体でフォワードプロキシ、
静的サイト、TLS ターミネーターとして動作します。

### セキュリティとアクセス制御

- OIDC 認証（`auth.method = "oidc"`）。標準準拠の任意の IdP（Keycloak、Google、Azure AD など）に対応。クライアントは Client Credentials グラントを使い、サーバーは JWKS 署名を検証（RS256 / PS256 / ES256）
- RBAC ロールテーブル（`[[roles]]`）。順序どおりに照合し、`deny_unknown` / `default_role` でフォールバック
- IP 許可 / 拒否リスト（`[acl]`）。CIDR 記法に対応し、`deny` が優先。**v0.5.9 以降、データプレーンのすべての入口をカバー**（TCP / UDP プロキシ、vhost、VNet、xtcp ランデブー、ダッシュボード）
- 監査ログ（`[audit]`）。JSONL への追記とメモリ上のリングバッファ。無効時はオーバーヘッドなし。**v0.5.9 以降 `maxFileMB` によるローテーション**（既定 64、`.1` を 1 世代保持）
- 資格情報の比較は常に定数時間。HTTP リレーはホップバイホップヘッダーを除去し、`Host` を正規化し、CL+TE スマグリングを拒否
- ダッシュボードとクライアントのローカル UI は、**非ループバックアドレスにバインドしつつ資格情報がない場合、起動を拒否**します（緊急回避用に `allow_insecure_dashboard` / `allowInsecureRemote`）

セキュリティ修正はすべて 1 つの文書に統合しています（日付順、各回の原文を保持）。

**[SECURITY-ALL-FIXES.md](SECURITY-ALL-FIXES.md)** — 第 1 回から第 16 回、2026-10-04 〜 2026-10-25

各回の元レポート（SECURITY-FIXES-ROUND4..16.md）も証跡として残しています。
統合文書には各回の日付と結論、および「再現 / 修正方法 / 回帰テスト」を
記録しています。

### 運用とスケジューリング

- グループロードバランシング: 同じ `group` と `remote_port` を共有する複数プロキシを、最小接続数で分散
- ヘルスチェック: `tcp` / `http` プローブ。連続失敗でバックエンドを外し、回復後に自動で戻す
- 帯域制限: プロキシごとの `bandwidth_limit`（例 `1MB`）をトークンバケットで正確に適用
- リソース上限: クライアント数 / プロキシ数 / 転送接続数 / 保留キューなど 5 つの軸を制限し、すべてメトリクスとして公開
- ポート許可リスト: `allowPorts` + `maxPortsPerClient`
- ログの保存とローテーション: `log.to` + `log.maxDays` で日次分割と削除
- クライアントストアの永続化: 動的に追加したプロキシを保存し、再起動後に復元
- 設定のホットリロード: `log_level` やダッシュボードのパスワードを再起動なしで変更

### 可観測性と管理

- 内蔵 Web ダッシュボード + Prometheus `/metrics`（`enablePrometheus = true` で有効、既定は無効）+ 認証不要のヘルスエンドポイント。Basic 認証に対応
- ダッシュボードからプロキシの追加 / 削除、クライアントの切断が可能。設定編集や再起動は不要
- Dashboard API v2（`/api/v2/*`）: 統一されたエラーエンベロープ、ページネーション、安定した並び順。v1 エンドポイントの挙動は不変
- クライアントのローカル Web UI / API（`[webServer] port = 7400`）: トンネル / 接続 / トラフィックの確認と、プロキシの追加 / 削除
- CPU プロファイル: `pprofEnable = true` にすると、サーバーのダッシュボードとクライアントのローカル Web の両方が
  `GET /debug/pprof/profile?seconds=N` を提供（既定 10 秒、上限 60 秒）。Unix では
  protobuf を返し、Windows では明示的に 501（Rust の `pprof` は perf シグナル / `ucontext_t` を必要とする）
- SSH トンネルゲートウェイ（`sshTunnelGateway`）: サーバーに SSH サーバーを内蔵し、OpenSSH の
  `ssh -R` で `tcp` / `http` / `https` / `tcpmux` / `stcp` プロキシを直接登録できる。データプレーンは
  通常の作業接続を再利用。`authorizedKeysFile` が空でなければそのファイル内の公開鍵のみを受け付け、
  鍵のコメントが frp のユーザー名になる
- HTTP プラグイン（`httpPlugins`）: サーバーが `Login` / `NewProxy` / `CloseProxy` /
  `Ping` / `NewWorkConn` / `NewUserConn` のタイミングで外部 HTTP サービスを呼び出し、拒否や
  ログイン内容・プロキシ名 / metas の書き換えが可能。1 リクエストあたり 10 秒でタイムアウト

### NLink v1: ネゴシエーションで有効化する拡張レイヤー（デフォルトは無効）

標準の frp プロトコルは、トランスポート、セッション、認証、スケジューリングの
モデルを固定しています。要望の中には「実装が下手」ではなく、**プロトコルに
情報を載せる場所がない**ものが含まれます。たとえば接続マイグレーションには
トランスポート層の接続識別子が必要ですが、frp は TCP/TLS の上に yamux を
重ねているため、その場所が存在しません。

NLink は標準 frp wire protocol の上に重ねるレイヤーで、2 つの原則を通します。

1. **標準フレームは 1 バイトも変えない** — 拡張は独立した名前空間に置くので、
   公式 frp はこれらのバイトを決して見ません
2. **ネゴシエーションが成立しなければ存在しないのと同じ** — どちらか一方が
   非対応なら、挙動は 0.6.x と完全に同一です

**追加のラウンドトリップはゼロ。** クライアントは最初のプロトコルメッセージの
前に能力宣言を便乗させ（`NFRPLNK1` preamble）、サーバーは本来送る
`LoginResp._nlink` に確認結果を便乗させて返します。判別は先頭バイトだけに
依存し、`NFRPLNK1`、`FRP\0\x02\r\n`、`{` は互いに重ならないため誤判定しません。

| 能力 | 説明 |
|---|---|
| QUIC トランスポートと接続マイグレーション | 専用 ALPN `nfrp-nlink`。標準 QUIC とは別バケットで混ざらない |
| セッション再開 | プロセス単位の `ConnectionId` は変わらず、サーバーはプロキシのリスナー / ポート / vhost ルートを `resume_ttl` 秒そのまま保持 |
| ゼロトラスト認証 | 各作業接続が `v1.<exp>.<hmac>` トークンを伴い、`run_id + user + 有効期限` に束縛 |
| 細粒度レート制限 | ユーザー × プロキシ単位のトークンバケット。バーストに対応 |
| ポートノッキング | ポートは既定で不可視。正しいノック列でその IP に対して一時的に開放 |
| 作業接続のバッチ取得 | `BatchReq` 1 本で N 本の接続を得て、1 本ずつの往復を削減 |
| エンドツーエンド trace | 制御プレーンとデータプレーンが同じ trace id を共有 |

**デフォルトは無効**で、両端で明示的に有効化します。

```toml
# frps.toml
[nlink]
enable = true
quic_listen = "0.0.0.0:7000"   # 空なら QUIC を開かない
resume_ttl = 30

# frpc.toml
[nlink]
enable = true
resume = true
quic = true
```

**公式 frp との共存**: 公式 frps は preamble を理解せず、v1 のメッセージ
ヘッダーとしてエラーにします。クライアントはその失敗を捕捉し、**自動的に
標準モードへフォールバックして 1 回だけ再試行**し、ログに 1 行の警告を
残します。トンネルはそのまま動作します。

| 組み合わせ | 挙動 |
|---|---|
| NFrp × NFrp | ネゴシエーション結果に従って有効化 |
| NFrp × 公式 frp | 標準モードにフォールバック。機能は縮退するが**接続性に影響なし** |
| 公式 × 公式 | まったく影響なし |

`--no-default-features` でコンパイルすると拡張フィールドが丸ごと消え、
wire format は 0.6.x とバイト単位で同一になります。

## クイックスタート

### ビルド

```bash
cargo build --release
# 成果物: <target_directory>/release/nfrp-server (frps)、<target_directory>/release/nfrp-client (frpc)
# target_directory は `cargo metadata` に従う: CARGO_TARGET_DIR や
# `.cargo/config.toml` を設定している場合、成果物は ./target 配下ではない
```

Rust 1.75 以上が必要です。Windows では MSVC ツールチェーンを使います。

リリースパッケージをダウンロードすることもできます。内部のバイナリ名は
`frps` / `frpc` で公式と同じです。

### サーバー（公開ホスト）

```toml
# frps.toml
bind_addr = "0.0.0.0"
bind_port = 7000
token = "十分にランダムな秘密に置き換えてください"

# 任意: xtcp の真の P2P 用ランデブーポート（UDP を許可する）
p2p_port = 7002

# 任意: 内蔵ダッシュボード（/metrics は enablePrometheus = true も必要）
dashboard_port = 7500
dashboard_user = "admin"
dashboard_pwd = "強力なパスワードに置き換えてください"
```

```bash
./nfrp-server -c frps.toml
# コメント付きの完全なサンプル設定を生成:
./nfrp-server --gen-config frps.toml
```

### クライアント（内部ホスト）

```toml
# frpc.toml
server_addr = "your.server.com"
server_port = 7000
token = "サーバーと同じ秘密"

[[proxies]]
name = "ssh"
type = "tcp"
local_addr = "127.0.0.1:22"
remote_port = 6000
```

```bash
./nfrp-client -c frpc.toml
```

これで `your.server.com:6000` が内部ホストの 22 番ポートに転送されます。

### 公式 frp との相互接続

NFrp は公式 frp のどちら側でも動作し、双方向とも実測で確認しています。

| サーバー | クライアント | 状態 |
|---|---|---|
| nfrp frps | 公式 frpc（tcpMux on/off、TLS on、各種プロキシ） | 通過 |
| 公式 frps | nfrp frpc（tcp_mux on/off、TLS on、各種プロキシ） | 通過 |
| nfrp frps | 公式 frpc（stcp プロバイダー / ビジター） | 通過 |

**互換マーカーは変更できません**: `frpc -v` は引き続き裸の `0.71.0` を出力し、
wire magic とバージョン文字列、パッケージ内の `frps` / `frpc` という命名も
すべて維持しています。この 3 つを変えると、公式 frp およびサードパーティ
サービスとの相互接続が即座に壊れます。

## 設定

設定キーは公式 frp に揃えてあり、**元の `frps.toml` / `frpc.toml` をそのまま
使えます**（camelCase、`localIP` + `localPort` の 2 段式、`[metadatas]` なども
受け付けます）。

公式から**意図的に外している**点が 2 つあり、どちらも注意が必要です。

- `local_addr` は統合形式の `ip:port`（`127.0.0.1:8080`）で、公式の
  `localIP` + `localPort` の 2 段式ではありません。2 段式も受け付けますが、
  2 つの書き方を混在させないでください。
- ログローテーションは **UTC** の 0 時で行います（公式はローカル時刻）。
  ログのタイムスタンプ自体が UTC だからです。

コメント付きの完全なサンプルは
[`assets/frps.toml`](assets/frps.toml) と
[`assets/frpc.toml`](assets/frpc.toml) にあります。`--gen-config` で生成も
できます。

その他の注意点:

- **OIDC 配備では TLS が必須**です。OIDC の `privilege_key` は生のアクセストークンで、
  ログインメッセージに平文で現れます。暗号化されていない回路上で受動的に傍受した
  者は誰でも取得できます。
- **クライアントの `transport.tls` は暗号化のみで、対向の証明書を検証しません**
  （公式 frp と同じ挙動）。受動的な盗聴は防げますが中間者攻撃は防げません。
  公衆回線で直接接続し MITM 対策が必要な場合は、**外側**にもう 1 層 TLS を
  重ねてください。
- **v1 のログイン資格情報の強度は token に完全に依存します**。v0.5.7 以降、
  サーバーは**タイムスタンプの鮮度を検証**し（既定 ±300 秒、上の表を参照）、
  リプレイの範囲を「無期限」から「5 分」に狭めました。ただし窓内でのリプレイは
  依然可能で、**オフラインでの token 総当たりのコストは時間窓とは無関係**です
  ⇒ 公衆回線へ配備する場合は十分にランダムな token を使い、v2 / OIDC を優先して
  ください。
- **`user` はクライアントの自己申告で、サーバーは検証できません**。
  `[[roles]]` がなければ単なるラベルですし、**`[[roles]]` を設定しても同じ**です
  — 共有 token を持つ者は誰でも他人の `user` を名乗ってそのロールを得られます。
  ⇒ `[[roles]]` は**テナント分離ではありません**。誤操作を防ぐ層にすぎません
  （v0.5.7 以降、サーバーはこれについて起動時に警告を出します）。本当の分離が
  必要なら OIDC（検証済みの `sub` から身元を得る）を使うか、テナントごとに
  別 token を発行してインスタンスを分けて配備してください。
- **xtcp の「データはサーバーを経由しない」は「サーバーに対する防御」では
  ありません**: サーバーは `secret_key` を保持し `sid` を自分で生成するため、
  理論上 P2P のシークレットを計算できます。これは**経路上の第三者**に対する
  防御で、サーバー自身に対する防御ではありません。
- 内部の詳細を露出したくない場合は `detailed_errors_to_client = false`
  （既定は公式と同じ `true`）を設定してください。クライアントへ送るエラーが
  統一された短い文言になり、stcp/xtcp のトンネル名の列挙面も減ります。
- **UDP プロキシの返信先は制限されています**（v0.5.6 以降）: サーバーは
  「最近そのポートへ実際にパケットを送ってきた訪問元 IP」にのみ UDP を返します。
  これは frps が UDP リフレクターとして使われるのを防ぐためです。通常の
  クライアントは受け取ったアドレスにしか返さないため**感知しません**。
- サンプル設定には既定でプロキシが**含まれていません**。必要な箇所のコメントを
  外してください。SSH は既定で公開されなくなりました。

## 品質保証

```bash
cargo fmt --all -- --check                              # フォーマット
cargo clippy --workspace --all-targets -- -D warnings   # 静的解析、警告 0
cargo test --workspace                                  # 999 通過 / 0 失敗 / 13 ignored
```

`#[ignore]` の 13 件はすべて**実機ハードウェアまたは管理者権限を必要とする**
ものです（Windows の Wintun アダプター、Linux の TUN デバイス）。壊れたテストを
飛ばしているのではありません。

CI は push / PR のたびに同じ 3 つのゲートを実行し、さらに 3 つの OS での
全テスト、2 つの musl ターゲットへのクロスビルド、エンドツーエンドの
スモークテストを行います。

**詳細は [QUALITY.md](QUALITY.md)** にあります。ターゲット別のテスト表、
CI マトリクス、依存関係セキュリティが実際にどこまでカバーするか
（`cargo audit` / `deny` / `vet` はそれぞれ意味が異なります）、リリースゲート、
手動チェックリスト。

## リリースと配備

### Docker

```bash
docker build -t nfrp .
docker run --rm -p 17000:17000 -p 17002:17002/udp \
  -v $PWD/frps.toml:/etc/nfrp/frps.toml nfrp
```

イメージは非 root ユーザーで動作し、マルチステージの musl ビルドを使います。
最終イメージには 2 つのバイナリとサンプル設定だけが含まれます。

### 自分でパッケージする

パッケージング、署名、クロスコンパイル（Android NDK の環境変数を含む）、
リリースゲートの完全なコマンドは **[QUALITY.md](QUALITY.md)** にあります。

要約すると、`release.py pack` はビルドしたパッケージを展開し、中の `frps` /
`frpc` をソース成果物と sha256 で比較し、不一致なら非ゼロで終了します。
この手順は任意ではありません — 「パッケージ名もバージョンも正しいのに、
中のバイナリが前のバージョンだった」リリースが実際にあったからです。

## 現在の制限

- **VirtualNet の TUN デバイス**: Linux は `/dev/net/tun`（root または `CAP_NET_ADMIN` が必要）。
  **Windows は Wintun**（v0.6.6 以降で対応。管理者権限と、自分で用意した `wintun.dll` が必要。
  リポジトリには `#[ignore]` 付きの実機アダプター / 双方向 ping のデータプレーンテストがあり、
  管理者権限で手動実行する必要がある。DLL 不在とアクセス拒否のエラー経路は非管理者セッションで
  検証済みだが、今回は実機データプレーンを再実行していない）。
  macOS は未実装で、黙って失敗せず明確なエラーを返す
- 公式 0.71 の設定フィールドとの整合状況:

  **実装済み**: TLS 証明書グループ（`transport.tls.certFile` / `keyFile` / `trustedCaFile`、
  サーバー側 mTLS とクライアント証明書を含む）、`auth.tokenSource`（ファイル / 外部コマンド、
  クライアントとサーバー）、`includes`（クライアント設定の取り込み）、`quicBindPort`、
  `enablePrometheus`、`udpPacketSize`（両端。既定は公式の 1500 ではなく 65507 —— 下記参照）、
  クライアントの `useEncryption` / `useCompression`（公式 golib の AES-128-CFB + snappy
  ストリームに合わせて実装。単体テストとメモリ上の双方向は通過。公式 frpc との組み合わせ
  e2e は未実施）、`proxyURL`（HTTP CONNECT / SOCKS5 の外向きプロキシ）、
  `dnsServer`（A/AAAA 問い合わせを独自の UDP DNS で解決）、`natHoleStunServer`（RFC 5389
  によるパブリックマッピング検出）、`pprofEnable`（Unix の CPU プロファイル、Windows は明示的に 501）、
  `assetsDir`（ダッシュボードの静的リソースディレクトリ）、`natholeAnalysisDataReserveHours`
  （NatHole 分析記録の保持期間、0 で保持しない）、`httpPlugins`（サーバー側のログイン / プロキシ /
  作業接続コールバック）、`sshTunnelGateway`（OpenSSH `ssh -R` トンネルゲートウェイ）。

  **公式 NatHole / xtcp**: 公式コントローラープロトコルを実装し、公式 `frpc 0.71.0` との
  実 e2e も行った（provider / visitor が `NatHoleSid` 作業接続、`NatHoleClient`、
  `NatHoleResp` を経て UDP ホールパンチングを完了し、アクセスに成功）。

  公式 `pkg/nathole/{classify,analysis}.go` に従い、**NAT 分類と mode 0〜4 の挙動選択を
  完全に実装**している: 双方 EasyNAT なら mode 0、片側 HardNAT ならポートが規則的に変化するかで
  mode 1 / 2、双方 HardNAT なら mode 3 / 4、どちらも不規則なら mode 0 の「とりあえず試す」に
  戻る。ポート予測（`portsRangeNumber` / `portsRandomNumber`）、ランダム待ち受けポート
  （`listenRandomPorts`）、TTL、`sendDelayMs` / `readTimeoutMs`、および全 STUN 候補アドレスも
  クライアントへ送信される。

  > 以前の版ではここに「mode 0 のみ対応」と書いていたが、それは 0.7.2 より前の古い結論で
  > あり、無効である。この能力の欠落は 0.7.4 で `mode_选择的六个分支与官方一致` というテストに
  > よって固定され、6 つの分岐のどれかが壊れれば赤になる。

  現実的な制限は残る: 実際に穴が開くかどうかは**両端の NAT 機器の実際の挙動**に依存する。
  HardNAT で失敗した場合、クライアントは `fallbackTo` に従ってリレーへ戻る —— これは
  設計された縮退経路である。

  **まだ未実施**: 実際の外部 IdP（Keycloak / Azure AD など）に対する OIDC 相互運用の
  e2e（現在はローカルのモック IdP に対して 9 件）。SSH ゲートウェイの tcpmux / stcp は
  登録と後始末までしか検証しておらず、**データプレーンの e2e はない**。

  > ~~`webServer.tls.certFile` / `webServer.tls.keyFile`（ダッシュボード HTTPS）は未実装~~
  > —— **訂正**: ダッシュボード HTTPS は v0.6.x 以降で実装済みで、実際の HTTPS + HSTS
  > 回帰テスト（`server/src/dashboard.rs::web_server_tls_真实_https_和_hsts`）もある。
  > 元の記述は履歴を書き換えないために残しており、現在の状態はこの行による。

  > `udpPacketSize` の既定値は**意図的に公式と異なる**: 公式の既定は 1500 だが、NFrp は
  > 一貫して 65507（UDP の上限）を使ってきた。1500 に変えると既存利用者の大きな UDP データグラムが
  > **黙って切り捨てられる**（パケットは届くが内容が欠ける）—— エラーより遥かに原因究明が難しい。
  > 公式の挙動に合わせたい配備では `udpPacketSize = 1500` を明示的に設定すればよい。
