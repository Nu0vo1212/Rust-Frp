NLink 是 NFRp 在标准 frp 协议之外的扩展层。它只承载那些 **frp 协议本身没有位置表达**、且 **确实有用户被卡住** 的能力。

:::callout 当前状态：已实现（v0.7.0 起，默认关闭）
下面列出的能力**均已实现并通过测试**（`server/tests/nlink_e2e.rs` 的 11 条端到端用例逐项覆盖）。
但 NLink **默认关闭**：服务端与客户端都要显式写 `[nlink] enable = true` 才生效。
不开启时，行为与 0.6.x 完全一致。
:::

## 握手：零额外往返

客户端把能力声明**搭车**在第一条协议消息之前，服务端把确认结果**搭车**在本就要发的
`LoginResp` 上带回。全程不新增任何往返。

```text
frpc                                          frps
 │                                             │
 ├─ [8] NFRPLNK1        魔术字                 │   首字节 'N' 是标准 frp
 ├─ [1] ver = 1         扩展版本               │   永远不产生的值
 ├─ [8] caps            能力位图（大端 u64）    │   （v1 首字节是 '{'）
 ├─ [16] session_id     进程级连接标识          │   （v2 是 'F'，TLS 是 0x16）
 ├─ [8] trace_id        端到端追踪              │
 ├─ 标准 v1/v2 握手 ────────────────────────▶ │
 │                                             ├─ 解析 preamble
 │                                             ├─ 协商结果 = 编译期实现
 │                             ◀────────────── ┤            ∩ 对端声明
 │  LoginResp { _nlink: { caps, session, ... } }│            ∩ 运行期允许
 │                                             │
 ├─ 后续扩展帧（与标准消息同一条流，同为密文） │
```

**为什么不会误判**：识别只依赖首字节。`MAGIC_V2` 是 `FRP\0\x02\r\n`，NLink 是
`NFRPLNK1`，v1 的 JSON 以 `{` 开头 —— 三者互不重叠。

探测统一读 `max(8, 7) = 8` 字节。早期实现按 `MAGIC_V2.len()`（7）去填，紧接着
切片到 8 字节做比较 —— 一个**只发 7 字节就闭嘴**的客户端就能把服务端 panic 掉。
现在这条有专门的回归测试（`首帧不足时_detect_version_报错而不是_panic`）。

## 扩展帧：版本化 TLV

```text
u8   version    扩展帧版本（当前 1）
u8   kind       帧种类
u16  flags      保留，必须为 0（不认识就忽略）
TLV*            每个：u16 tag + u32 len + len 字节
```

**对方不认识的 `kind` 或 `tag` 必须跳过，不能报错** —— 这是前向兼容的唯一前提。
帧长度自描述，所以跳过是安全的。

v2 侧走专用帧类型 `0x4E`；v1 侧走专用消息类型字节 `0x7F`。这两个值官方到
v0.71.0 为止都没用过（官方 v1 的类型字节都是可打印 ASCII），所以不会撞号。

## 各能力的承载方式

| 能力 | 承载 | 说明 |
|---|---|---|
| 能力协商 | preamble + `LoginResp._nlink` | 双方交集非空才启用 |
| QUIC 与连接迁移 | 独立 ALPN `nfrp-nlink` | 与标准 QUIC 分桶，互不串味 |
| 断线续传 | `session_id` + 服务端保留表 | 保留 `resume_ttl` 秒，重连后原样恢复 |
| 零信任身份 | `NewWorkConn._nlink` 令牌 | `v1.<exp>.<hmac>`，绑定 `run_id + user + 过期时间` |
| 细粒度限流 | 桥接层令牌桶 | 按「用户 × 代理」，支持突发 |
| 端口敲门 | 数据面 33 字节序列 | 敲对了按 IP 临时放行 |
| 批量工作连接 | `BatchReq` | 一条帧换 N 条连接 |
| 端到端 trace | `trace_id` | 控制连接与数据面共享 |

## 怎么开启

```toml
# frps 端
[nlink]
enable = true
# features = ["quic", "resume", "trace"]   # 留空 = 只协商、不启用任何一项
quic_listen = "0.0.0.0:7000"               # 留空 = 不开 QUIC
resume_ttl = 30                            # 断线续传保留时长（秒）
```

```toml
# frpc 端
[nlink]
enable = true
resume = true      # 断线后用同一个 connection id 续传
quic = true        # 走 QUIC 连服务端（需服务端开 quic_listen）
```

官方面（官方 frpc/frps）不认 preamble，会把首字节当成 v1 消息头报错。
客户端捕获到这种失败后**自动回退标准模式并只重试一次**，日志里留一行 warn，隧道照常工作。

## 为什么需要扩展层

frp 的协议是够用的，但它把「传输、会话、鉴权、调度」都固定死了。有些问题不是"实现得不好"，而是 **协议里根本没有承载位置** —— 比如连接迁移需要传输层有独立的连接标识，而 frp 是在 TCP/TLS 之上套 yamux，这个位置不存在。

## 准入判断：四个门槛必须同时成立

| 门槛 | 含义 |
|---|---|
| **① 协议层无解** | 不是"frp 实现得差"，而是 **协议本身** 没有字段、没有流程、没有语义可以承载 |
| **② 有明确需求** | 能说清"谁在什么场景被卡住"，而不是"技术上可以做" |
| **③ 必须双端** | 单端升级做不到，或单端做出来是残缺的 |
| **④ 可回退** | 对端不支持时必须能 **无损退回** 标准 frp |

第 ④ 条是硬门槛。做不到可回退的，不进 NLink。

## 候选清单

| # | 功能 | 为什么 frp 协议根本解决不了 | 用户需求场景 |
|---|---|---|---|
| 1 | **原生 QUIC / 多路复用与连接迁移** | frp 的传输层是「先建 TCP/TLS，再套 yamux」。连接迁移要求 **连接标识与四元组解耦**，这是传输层语义，在 yamux 之上做不了。QUIC 的 `connection_id` 在 frp 里没有承载位置。 | 移动网络切换 Wi-Fi↔4G 时连接全断；弱网下 TCP 队头阻塞导致所有隧道一起卡。 |
| 2 | **更强的 P2P 打洞信令与 NAT 类型自适应** | 官方 `NatHoleVisitor` / `NatHoleResp` 只承载「行为模式 0~4 + 地址列表」，**没有** 双向持续探测、没有 TTL 探测结果回传、没有失败原因码。打洞失败只能重试或退回中继。 | 对称 NAT / 双防火墙下的打洞成功率；现在只能"试不成拉倒"。 |
| 3 | **零信任身份、细粒度流控、端到端可观测性** | 鉴权是 **连接级一次性**（token / OIDC 登录），没有每请求身份；流控只有 `bandwidthLimit` 粗粒度；追踪信息不跨段透传。 | 多租户场景要按代理 / 用户 / 请求维度限流与审计；排障要端到端 trace。 |
| 4 | **大规模海量连接下的头部开销与调度模型** | 每条工作连接都要走一次 `StartWorkConn` JSON 握手。协议里没有 **「批量申请工作连接」** 的语义。 | 单 frps 承载 5 万+ 连接时，连接建立延迟与内存开销明显。 |
| 5 | **移动端弱网切换、断线续传** | 断线后只能 **重连重建代理**，没有「会话恢复」语义（`run_id` 是登录期生成的，工作连接无法跨断线复用）。续传需要可恢复的流标识 + 服务端保留状态，协议层没有。 | 地铁 / 电梯 / 切网掉线后，所有隧道重建、长连接业务全断。 |

## 附带补齐

下面三项性质与上面五条 **不同**：它们不是"协议无解"，而是需求或兼容性缺口。列出来是为了完整，但按 ① 号门槛严格说，它们不满足"根本解决不了"。

| 项 | 性质 | 说明 |
|---|---|---|
| **端口敲门** | 需求驱动，*非协议无解* | frp 的端口一旦开放就对外可见，扫描器能发现。敲门是「先敲门再开放」的访问控制模式，可用扩展帧承载敲门序列，通过后临时放行。 |
| **XTCP 混合版本直连策略** | 兼容性缺口 | 官方 frpc 与我们并存时，直连能力协商不一致会导致「一方以为能打洞、另一方在等中继」。需要显式的版本 / 能力交集策略。 |
| **与官方双向兼容的边界行为** | 兼容性澄清 | 明确列出「官方会忽略哪些字段」「官方会报错哪些」「哪些情况我们比官方更严」，形成可测试的边界用例集。 |

## 五条硬性工程约束

这五条是 NLink v1 的设计底线，任何一条不满足就不合入。

### 1. 握手期能力协商

握手阶段交换 capabilities，**双方都支持才启用扩展**，否则自动回退标准 frp 行为。协商在登录 / 握手阶段完成，不额外增加往返；能力用位图 + 版本号表示，**未知位一律忽略**（前向兼容）；协商结果决定本次连接的全部行为，中途不改。

### 2. 版本化 TLV / 扩展帧

扩展帧放在 **独立命名空间**（专用消息类型 / 专用 TLV 编号段），**绝不改变标准帧语义** —— 标准帧的字段、顺序、含义一律不动。TLV 带版本号，对方不认识的 TLV 必须 **跳过而非报错**。扩展帧长度必须自描述，便于跳过。

### 3. Feature flag

默认 **关闭**，或默认 **「仅协商不启用」**（会声明能力、但只在显式开启时才真正使用）。编译期 flag（`--features`）与运行期开关两层都要有。**关闭时零开销**：不产生额外字段、不改变报文长度。

### 4. 双栈共存

**同一端口** 能识别标准 frp 握手与扩展握手；识别依据只能是「标准 frp 不会产生的特征」（首字节 / 魔术字）。扩展握手失败 ⇒ **自动 fallback** 到标准流程，用户无感。

### 5. 迁移工具与兼容性矩阵

提供迁移工具（配置转换、能力检测、兼容性自检），并维护兼容性矩阵，明确标注每个功能的支持情况。矩阵必须 **可测试**：每一行都要有对应的 e2e 用例。

## 兼容性矩阵

| 功能 | NFrp × NFrp | NFrp × 官方 frp | 官方 × 官方 |
|---|---|---|---|
| 原生 QUIC / 连接迁移 | 支持 | 回退 TCP | 不支持 |
| 增强打洞信令 | 支持 | 降级为官方 NatHole | 官方行为 |
| 零信任身份 / 细粒度流控 | 支持 | 仅 metadata 透传 | 不支持 |
| 批量工作连接 | 支持 | 逐条建 | 不支持 |
| 断线续传 | 支持 | 重连重建 | 不支持 |
| 端口敲门 | 支持 | 不支持 | 不支持 |
| XTCP 混合版本直连 | 支持 | 需显式策略 | 官方行为 |

## 建议的实施顺序

按「依赖关系 + 风险从低到高」排：

| 阶段 | 内容 | 理由 |
|---|---|---|
| **0. 地基** | 能力协商 + TLV 框架 + 双栈识别 + feature flag | 后面所有功能都挂在这套地基上，必须先做且做对 |
| **1. 低风险** | XTCP 混合版本策略、兼容性矩阵与边界用例集 | 纯策略与测试，不改协议核心，先把兼容性说清楚 |
| **2. 独立** | 端口敲门、批量工作连接 | 各自独立、互不依赖，可并行 |
| **3. 打洞** | 增强信令 + NAT 自适应 | 依赖打洞实测环境（多网卡 / 可控 NAT） |
| **4. 传输层** | 原生 QUIC + 连接迁移 | 改动最大，地基要稳 |
| **5. 会话** | 断线续传 | 依赖服务端保留状态，必须最后做 |
| **6. 可观测** | 零信任身份 + 细粒度流控 + 端到端 trace | 横切面，等前面稳定后再加 |

## 明确不做

| 想法 | 为什么不做 |
|---|---|
| 改标准帧的字段含义 | 破坏与官方的兼容，违反约束 2 |
| 让扩展成为默认 | 风险不可控，违反约束 3 |
| 在 yamux 之上模拟连接迁移 | 语义错了 —— 迁移必须在传输层；模拟出来的东西不解决问题 |
| 把鉴权从「连接级」改成「每帧」 | 会对不支持的对端产生不兼容；应做成可选扩展 |
| 自定义压缩 / 加密算法 | 已有 `useCompression` / `useEncryption` 与官方逐字节对齐，改算法只会破坏互通 |

## 每个功能立项时必须回答的问题

避免做成「技术上很酷但没人用」：

1. 现在的 frp 具体卡在哪一步？（要能指到协议字段 / 流程）
2. 谁在什么规模下遇到？（用户画像 + 量化场景）
3. 不做会怎样？（绕路方案的成本）
4. 双端升级的实际成本？（老客户端留存率）
5. 回退路径是什么？回退后功能残缺到什么程度？
6. 怎么证明做成了？（可测试的验收标准）
7. 对官方 frpc 的兼容性影响？（必须是「零影响」或「可协商降级」）
