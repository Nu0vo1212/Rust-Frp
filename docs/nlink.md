NLink 是 NFrp 在标准 frp 协议之外的扩展层。它只承载那些 **frp 协议本身没有位置表达**、且 **确实有用户被卡住** 的能力。

:::callout 当前状态：已实现（v0.7.4 起，默认关闭）
下面列出的能力**均已实现并通过测试**（`server/tests/nlink_e2e.rs` 的 16 条端到端用例逐项覆盖）。
但 NLink **默认关闭**：服务端与客户端都要显式写 `[nlink] enable = true` 才生效。
不开启时，行为与 0.6.x 完全一致。
:::

## 握手：零额外往返

客户端把能力声明**搭车**在第一条协议消息之前，服务端把确认结果**搭车**在本就要发的
`LoginResp` 上带回。全程不新增任何往返。

```text
frpc                                          frps
 │                                             │
 ├─ [8] NFRPLNK1        魔术字                 │   首字节 'N' 是标准 frp
 ├─ [1] ver = 1         扩展版本               │   永远不产生的值
 ├─ [8] caps            能力位图（大端 u64）    │   （v1 首字节是 '{'）
 ├─ [16] session_id     进程级连接标识          │   （v2 是 'F'，TLS 是 0x16）
 ├─ [8] trace_id        端到端追踪              │
 ├─ 标准 v1/v2 握手 ────────────────────────▶ │
 │                                             ├─ 解析 preamble
 │                                             ├─ 协商结果 = 编译期实现
 │                             ◀────────────── ┤            ∩ 对端声明
 │  LoginResp { _nlink: { caps, session, ... } }│            ∩ 运行期允许
 │                                             │
 ├─ 后续扩展帧（与标准消息同一条流，同为密文） │
```

**为什么不会误判**：识别只依赖首字节。`MAGIC_V2` 是 `FRP\0\x02\r\n`，NLink 是
`NFRPLNK1`，v1 的 JSON 以 `{` 开头 —— 三者互不重叠。

探测统一读 `max(8, 7) = 8` 字节。早期实现按 `MAGIC_V2.len()`（7）去填，紧接着
切片到 8 字节做比较 —— 一个**只发 7 字节就闭嘴**的客户端就能把服务端 panic 掉。
现在这条有专门的回归测试（`首帧不足时_detect_version_报错而不是_panic`）。

## 扩展帧：版本化 TLV

```text
u8   version    扩展帧版本（当前 1）
u8   kind       帧种类
u16  flags      保留，必须为 0（不认识就忽略）
TLV*            每个：u16 tag + u32 len + len 字节
```

**对方不认识的 `kind` 或 `tag` 必须跳过，不能报错** —— 这是前向兼容的唯一前提。
帧长度自描述，所以跳过是安全的。

v2 侧走专用帧类型 `0x4E`；v1 侧走专用消息类型字节 `0x7F`。这两个值官方到
v0.71.0 为止都没用过（官方 v1 的类型字节都是可打印 ASCII），所以不会撞号。

## 各能力的承载方式

| 能力 | 承载 | 说明 |
|---|---|---|
| 能力协商 | preamble + `LoginResp._nlink` | 双方交集非空才启用 |
| QUIC 与连接迁移 | 独立 ALPN `nfrp-nlink` | 与标准 QUIC 分桶，互不串味 |
| 断线续传 | `session_id` + 服务端保留表 | 保留 `resume_ttl` 秒，重连后原样恢复 |
| 零信任身份 | `NewWorkConn._nlink` 令牌 | `v1.<exp>.<hmac>`，绑定 `run_id + user + 过期时间` |
| 细粒度限流 | 桥接层令牌桶 | 按「用户 × 代理」，支持突发 |
| 端口敲门 | 数据面 33 字节序列 | 敲对了按 IP 临时放行 |
| 批量工作连接 | `BatchReq` | 一条帧换 N 条连接 |
| 端到端 trace | `trace_id` | 控制连接与数据面共享 |

:::callout 续传的认证边界
从 0.7.4 起，续传需要出示**服务端签发的一次性令牌**，光知道 `session_id` 不再够用。

令牌用 HMAC 绑定 `session + user + client_id + 过期时间 + 随机 nonce`，
登记在待用表里，**用一次就作废**。它在登录成功时通过 `ResumeResp` 下发
（断线时连接已经断了，发不出去，所以必须提前给）。

这样"抄走 preamble 就能冒充"这条路堵上了：伪造不出签名，重放上一轮的令牌
也会因为已被消费而失败。

**但仍有一处需要你自己判断**：`transport.tls.force = false`（默认值）时，
链路上的观察者可以**直接抄走令牌并抢先消费**。这时真客户端会续传失败并告警——
可检测，但拦不住。**生产环境请开 `transport.tls.force = true`**，
让令牌本身也在加密通道里。
:::

## 续传后的代理对账

续传保住的是"会话身份 + 监听器 + 端口"，但**代理清单可能已经变了**——
客户端在断线期间可能改过配置、删了某个代理。所以续传成功后客户端要把
"最终还在的代理"报上来，服务端据此回收没被提到的那些。

这条帧叫 `ResumeCommit`，走 `TAG_DETAIL` 承载代理名（换行分隔）。

### 名单大了怎么办：自动分片

一帧的上限是 8192 字节。代理多的时候一份名单装不下，0.7.2 之前客户端只能
**拒绝发送并记日志** —— 续传照样成功，但"删掉的代理立即回收"这个能力会
静默降级成 10 秒宽限期。

现在客户端自动分片：每片带 `TAG_CHUNK`（片序号）与 `TAG_CHUNKS`（总片数），
服务端收齐才结算。

- **只有一片时不带分片标记**，线上格式与 0.7.1 完全一致，老服务端照常解析；
- 分片按**代理名边界**切，不会切断单个名字；
- 乱序到达能正确重组；重复到达不重复计入；新一轮分片会重置旧状态。

### 上限

| 限制 | 值 | 说明 |
|---|---|---|
| 名单总字节 | **8 MiB** | 按每个代理名 40 字节算约 20 万个 —— 远超单机 frps 的实际承载量 |
| 分片数 | 由字节预算推出（约 1100 片） | `TAG_CHUNKS` 是 u16，不会溢出 |

这两个上限都是**防 DoS**的：没有它们，恶意客户端可以一直发分片让服务端攒内存，
或者声称一个巨大的总片数却永远不发完。超过预算会被拒绝并记 warn，不影响会话本身。

> 0.7.2 原本写的是"最多 64 片"（约 512 KiB / 1.3 万代理）。0.7.4 改成按
> **字节预算**限制，这样 `MAX_FRAME` 将来变化时语义也不会漂移。

## 怎么开启

```toml
# frps 端
[nlink]
enable = true
# features = ["quic", "resume", "trace"]   # 留空 = 只协商、不启用任何一项
quic_listen = "0.0.0.0:7000"               # 留空 = 不开 QUIC
resume_ttl = 30                            # 断线续传保留时长（秒）
```

```toml
# frpc 端
[nlink]
enable = true
resume = true      # 断线后用同一个 connection id 续传
quic = true        # 走 QUIC 连服务端（需服务端开 quic_listen）
```

官方面（官方 frpc/frps）不认 preamble，会把首字节当成 v1 消息头报错。
客户端捕获到这种失败后**自动回退标准模式并只重试一次**，日志里留一行 warn，隧道照常工作。
## 为什么需要扩展层

frp 的协议是够用的，但它把「传输、会话、鉴权、调度」都固定死了。有些需求不是
"实现得不好"，而是**协议里根本没有承载位置**——比如连接迁移需要传输层有独立的
连接标识，而 frp 是在 TCP/TLS 之上套 yamux，这个位置不存在。

NLink 就是在不改标准帧的前提下，补上这些位置。

## 能力清单

八项能力全部已实现，由 `server/tests/nlink_e2e.rs` 的 16 条端到端用例逐项覆盖。

| 能力 | 承载 | 说明 |
|---|---|---|
| 原生 QUIC 传输与连接迁移 | 独立 ALPN `nfrp-nlink` | 与标准 frp 的 `nfrp-frp` 分桶，同一 UDP 端口可并存 |
| 多路复用 | QUIC 流 | 一条 QUIC 连接跑多条隧道，弱网下不受 TCP 队头阻塞牵连 |
| 断线续传 | `session_id` + 一次性令牌 + 服务端保留表 | 保留 `resume_ttl` 秒（默认 30），**恢复的是监听器/端口/vhost/visitor 本体**，不只是名单。令牌单次有效，见下方认证边界 |
| 零信任身份 | `NewWorkConn._nlink` 令牌 | `v1.<exp>.<hmac>`，绑定 `run_id + user + 过期时间`，伪造和过期都被拒 |
| 细粒度限流 | 桥接层令牌桶 | 按「用户 × 代理」共享桶，支持突发；低速率时自动缩小 relay chunk |
| 端口敲门 | 数据面 33 字节序列 | 端口默认对外不可见，敲对后按 IP 临时放行（窗口可配） |
| 批量工作连接 | `BatchReq` 帧 | 一条帧换 N 条连接，省掉逐条 `StartWorkConn` 的往返 |
| 端到端 trace | `trace_id` | 控制连接与数据面共享同一个 id |

**设计上的补充**：XTCP 混合版本直连策略、与官方双向兼容的边界用例集，
也一并落地（见下方兼容性矩阵）。

## P2P 打洞：NatHole 的五种 mode

服务端按官方 `pkg/nathole/{classify,analysis}.go` 实现了完整的行为选择，
**mode 0~4 全都在用**，不是只有 EasyNAT 的 mode 0。

判定依据是双方 NAT 特征的三个计数：`easyCount` / `hardCount` /
`portsChangedRegularCount`。

| 条件 | 首选 mode | 含义 |
|---|---|---|
| 双方都 EasyNAT | **mode 0** | 映射稳定，直接对发即可 |
| 一方 HardNAT + 端口规律变化 | **mode 1** | 预测端口范围扫描 |
| 一方 HardNAT + 端口不规律 | **mode 2** | TTL 控制 + 多轮重试 |
| 双方 HardNAT + 都规律 | **mode 3** | 双向预测 + 随机监听端口 |
| 双方 HardNAT + 一方规律 | **mode 4** | 单侧预测 + 随机监听端口 |
| 双方 HardNAT + 都不规律 | mode 0（分数 1） | 极难，硬着头皮试 |

每张行为表都还按「历史成功率」打分：续传/重试时优先选之前成功过的
mode + index，成功后分数 +2（上限 10），由客户端通过 `NatHoleReport` 回报。

配套参数也一并下发：`portsRangeNumber` / `portsRandomNumber`（端口预测范围）、
`listenRandomPorts`（随机监听端口数）、`ttl`、`sendDelayMs`、`readTimeoutMs`、
以及全部 STUN 候选地址 `candidateAddrs`。

**仍然存在的限制**：这些是**协议层的能力**，最终能不能打洞成功还取决于
两端 NAT 设备的实际行为。HardNAT 场景下失败仍会按 `fallbackTo` 退回中继——
这是设计好的降级路径，不是缺陷。

## 设计约束

这五条是 NLink 的硬约束。不满足就不合入——它们是这份协议能被安全启用的前提。

### 1. 握手期能力协商

双方都声明才启用，否则自动回退标准 frp 行为；协商结果决定本次连接的全部行为，
中途不改。能力用位图 + 版本号表示，**未知位一律忽略**（前向兼容）。

### 2. 版本化 TLV / 扩展帧

扩展帧放在**独立命名空间**，**绝不改变标准帧语义**——标准帧的字段、顺序、
含义一律不动。对方不认识的 TLV 必须**跳过而非报错**。帧长度自描述，跳过是安全的。

### 3. 两层开关，关闭即零开销

编译期 `nlink` feature（默认开）+ 运行期 `[nlink] enable`（**默认 false**）。

用 `--no-default-features` 编译时，`LoginResp` / `NewWorkConn` 的 `_nlink` 键
**根本不存在**，报文与 0.6.x 逐字节一致。这一点是实测验证的（`cargo tree
--no-default-features` 中不含 nlink）。

### 4. 双栈共存

**同一端口**识别两种握手，只依赖首字节——`NFRPLNK1`、`FRP\0\x02\r\n`、`{`
三者互不重叠。扩展握手失败自动 fallback，用户无感。

### 5. 可测试性

兼容性矩阵的每一行都有对应的 e2e 用例。NLink 相关的 e2e 共 16 条，
覆盖续传、身份、敲门、限流、QUIC、门控与旧客户端回退。

## 兼容性矩阵

| 功能 | NFrp × NFrp | NFrp × 官方 frp | 官方 × 官方 |
|---|---|---|---|
| QUIC 传输 / 连接迁移 | 支持 | 回退 TCP | 不支持 |
| 断线续传 | 支持 | 重连重建 | 不支持 |
| 零信任身份 | 支持 | 不启用（令牌不出现） | 不支持 |
| 细粒度限流 | 支持 | 不启用 | 不支持 |
| 批量工作连接 | 支持 | 逐条建 | 不支持 |
| 端口敲门 | 支持 | 不支持 | 不支持 |
| 端到端 trace | 支持 | 不启用 | 不支持 |
| XTCP 混合版本直连 | 支持 | 需显式策略 | 官方行为 |

**与官方 frp 的全部交互都是"不启用"，不影响连通性。** 唯一需要特殊处理的是
preamble：官方 frps 会把它当 v1 消息头报错，客户端捕获后回退标准模式重试一次。

## 续传的认证边界（重要）

续传身份是 **`user` + `client_id` + `session_id`** 的 bearer 会话，不是一次性凭证。

**当 `transport.tls.force = false`（默认值）时**，preamble 与登录凭据在链路上是明文。
能观察到有效 token 的人，可以抢在原客户端之前完成续传，占住原会话的代理与端口。

本版的处置：

- 服务端若开了续传但没强制 TLS，**启动时打告警**；
- 文档记录此边界（就是你正在读的这一节）；
- 明确建议：**生产环境开 `transport.tls.force = true`**。

彻底修复需要一次性 resume token（签发 + 消费语义），不在当前版本范围内。

## 明确不做

| 想法 | 为什么不做 |
|---|---|
| 改标准帧的字段含义 | 破坏与官方的兼容，违反约束 2 |
| 让扩展默认开启 | 风险不可控，违反约束 3 |
| 在 yamux 之上模拟连接迁移 | 语义错了——迁移必须在传输层，模拟出来的东西不解决问题 |
| 把鉴权从「连接级」改成「每帧」 | 会对不支持的对端产生不兼容；应做成可选扩展 |
| 自定义压缩 / 加密算法 | 已有 `useCompression` / `useEncryption` 与官方逐字节对齐，改算法只会破坏互通 |
