---

NFrp — это реализация [fatedier/frp](https://github.com/fatedier/frp) на Rust.
Она **полностью совместима с официальным протоколом передачи данных, и v1, и v2**,
и напрямую работает с официальными `frps` / `frpc` (проверено на v0.71.0).
Конфигурации, которые выдают сторонние frp-платформы, подходят без изменений.

По умолчанию используется **v1**, как и в официальном frp, поэтому официальным
клиентам и серверам **не нужно менять настройки**, чтобы подключиться.

Потребление памяти невелико: сервер занимает около 3,5 МБ резидентной памяти
(Go-версия frps при той же нагрузке — 28,8–31,8 МБ). Один бинарный файл,
без зависимостей времени выполнения.

Есть также необязательный слой расширений **NLink v1** (транспорт QUIC и
миграция соединений, возобновление сессий, zero-trust идентификация,
тонкая настройка ограничения скорости, port knocking). Он **выключен по
умолчанию**, включается по согласованию обеих сторон и полностью обратим —
на официальный frp не влияет. См. [NLink v1](#nlink-v1-расширение-по-согласованию-по-умолчанию-выключено).

> **Полная документация**: <https://nu0vo1212.github.io/Rust-Frp/>
> Установка, все параметры конфигурации, восемь типов прокси, протоколы v1/v2,
> ACL / RBAC, журнал аудита, HTTP API и история исправлений безопасности.
> Исходники в [`docs/`](docs/), локальный просмотр:
> `python -m http.server -d docs 8899`
>
> **Качество и релизы**: [QUALITY.md](QUALITY.md) — распределение тестов,
> матрица CI, что именно покрывает проверка зависимостей, релизные «ворота»
> и ручной чек-лист.

## Установка

### Вариант 1: crates.io (рекомендуется для пользователей Rust)

Все три крейта опубликованы. Можно также зависеть только от библиотеки
протокола и **не запускать сервер туннелей**:

```bash
# Установить оба исполняемых файла
cargo install nfrp-server nfrp-client
```

```toml
# Или: использовать протокол / конфигурацию / шифрование как библиотеку
[dependencies]
nfrp-common = "0.7"
```

| крейт | Назначение | Ссылки |
|---|---|---|
| **nfrp-common** | Протокол, конфигурация, шифрование, ACL/RBAC, журналирование, абстракции транспорта | [crates.io](https://crates.io/crates/nfrp-common) · [docs.rs](https://docs.rs/nfrp-common) |
| **nfrp-server** | Исполняемый файл сервера (аналог официального `frps`) | [crates.io](https://crates.io/crates/nfrp-server) |
| **nfrp-client** | Исполняемый файл клиента (аналог официального `frpc`) | [crates.io](https://crates.io/crates/nfrp-client) |

> **О номерах версий**: версии на crates.io и версии релизов на этой странице
> **независимы**. Например, релиз может быть `v0.7.1`, а на crates.io уже
> `0.7.2` — crates.io не позволяет повторно публиковать тот же номер версии,
> поэтому даже правка README требует повышения версии.
> **Поведение кода смотрите по релизу**; `cargo install` всегда даёт последнюю
> опубликованную версию крейта.
>
> ★ **Бинарный файл из `cargo install` — не та же сборка, что одноимённый
> файл в релизе.** Пример `0.6.6`: сборка для crates.io была сделана до релиза,
> затем было ещё несколько правок, после чего поставили тег `v0.6.6` (номер уже
> был занят, повторно опубликовать нельзя). Поэтому
> **`cargo install nfrp-server@0.6.6` и `frps` из релизного пакета могут вести
> себя по-разному**. Если нужны воспроизводимые артефакты, на которые можно
> ссылаться в issue, используйте
> [вариант 2: скачать бинарные файлы](#вариант-2-скачать-бинарные-файлы).
> Начиная со следующих версий порядок фиксирован: **сначала публикация на
> crates.io, затем сборка релиза из той же сборки**.

Список модулей `nfrp-common`:

| Задача | С чего начать |
|---|---|
| Чтение/запись TOML-конфигурации frp (с совместимостью имён ключей) | `config` · `frp_config` |
| Разбор старого `frpc.ini` / `frps.ini` | `frp_legacy` |
| Реализовать собственный клиент или сервер frp | `frp` · `frp::msg` |
| Только шифрование (AEAD / v1 CFB) | `frp::crypto` · `frp::v1` · `frp::tls` |
| Разбор и пересылка HTTP (без веб-фреймворка) | `http1` · `http_relay` |
| Белые/чёрные списки IP, RBAC, аудит | `security` |
| Ежедневная ротация журналов | `logfile` |
| PROXY protocol v1/v2 | `proxy_protocol` |
| Транспорты KCP / QUIC / WebSocket | `frp::kcp` · `frp::quic` · `ws` |

## Возможности

### Типы прокси

Восемь — ровно столько же, сколько в официальном frp:

| Тип | Описание |
|---|---|
| `tcp` | Самый обычный проброс портов |
| `udp` | Проброс UDP; каждый прокси использует одно рабочее соединение, сессии различаются по адресу посетителя |
| `http` | Маршрутизация по домену: префиксы `locations`, Basic Auth, перезапись Host, свои заголовки запроса и ответа |
| `https` | Маршрутизация по SNI из ClientHello; TLS не терминируется, сертификаты остаются на внутреннем сервисе |
| `tcpmux` | Мультиплексирование HTTP CONNECT; несколько прокси делят один порт сервера, есть `routeByHTTPUser` для второго уровня маршрутизации |
| `stcp` | Приватный туннель; сервер не открывает публичный порт, `secret_key` и белый список `allow_users` |
| `sudp` | Та же схема аутентификации, что у stcp, но плоскость данных — UDP; публичный порт также не используется |
| `xtcp` | Пробивание UDP и прямое соединение по QUIC / KCP, данные минуют сервер. При неудаче автоматически возвращается к ретрансляции. С v0.5.8 в P2P-рукопожатии две проверки: провайдер возвращает **производный секрет ответа**, а сервер привязывает HELLO рандеву к IP контрольного соединения |

### Транспорты

- Двойной протокол frp v1 / v2; по умолчанию v1, включить v2 можно через `transport.wireProtocol = "v2"`
- Транспорт QUIC (`transport_protocol = "quic"`): рукопожатие за 1 RTT, мультиплексирование потоков
- KCP для плохих сетей: и как канал прямого соединения xtcp, и как самостоятельный транспорт (`kcp_bind_port`)
- Мультиплексирование yamux (`transport.tcpMux`): управляющее и рабочие соединения используют один TCP
- TLS (`transport.tls`), включая официальную маскировку первого байта. Сервер сам создаёт самоподписанный сертификат; можно указать `certFile` / `keyFile`; `trustedCaFile` включает клиентские сертификаты (mTLS). Клиент может предъявить свою идентичность через `certFile` / `keyFile`
- WebSocket / WSS (`websocket = true`) с автоопределением по пути на том же порту — проходит через межсетевые экраны, разрешающие только HTTP
- Proxy Protocol v1 / v2 для передачи реального IP клиента в Nginx / HAProxy / приложение

### Клиентские плагины

Реализованы все девять официальных: `http_proxy` / `socks5` /
`static_file` / `unix_domain_socket` / `http2http` / `http2https` /
`https2http` / `https2https` / `tls2raw`. Сам frpc может быть форвард-прокси,
статическим сайтом или терминатором TLS.

### Безопасность и управление доступом

- Аутентификация OIDC (`auth.method = "oidc"`) с любым соответствующим стандарту IdP (Keycloak, Google, Azure AD и др.). Клиент использует Client Credentials, сервер проверяет подписи JWKS (RS256 / PS256 / ES256)
- Таблица ролей RBAC (`[[roles]]`) с сопоставлением по порядку и запасными вариантами `deny_unknown` / `default_role`
- Белые и чёрные списки IP (`[acl]`) в синтаксисе CIDR, `deny` имеет приоритет. **С v0.5.9 покрывают все точки входа плоскости данных** (TCP / UDP прокси, vhost, VNet, рандеву xtcp, панель)
- Журнал аудита (`[audit]`): дописывание JSONL и кольцевой буфер в памяти; при выключении накладных расходов нет. **С v0.5.9 ротация `maxFileMB`** (по умолчанию 64, одна резервная копия `.1`)
- Сравнение учётных данных всегда за постоянное время; HTTP-ретрансляция удаляет hop-by-hop заголовки, нормализует `Host` и отвергает контрабанду CL+TE
- Панель и локальный интерфейс клиента **отказываются запускаться, если слушают не loopback-адрес и не имеют учётных данных** (аварийные переключатели: `allow_insecure_dashboard` / `allowInsecureRemote`)

Все исправления безопасности собраны в один документ (в хронологическом
порядке, с сохранением исходного текста каждого раунда):

**[SECURITY-ALL-FIXES.md](SECURITY-ALL-FIXES.md)** — раунды с 1 по 16, 2026-10-04 … 2026-10-25

Отчёты по раундам (SECURITY-FIXES-ROUND4..16.md) сохранены как цепочка
свидетельств; в сводном документе для каждого раунда указаны дата и вывод,
а также воспроизведение, исправление и регрессионный тест.

### Эксплуатация и планирование

- Балансировка по группам: несколько прокси делят `group` и `remote_port`, распределение по наименьшему числу соединений
- Проверки работоспособности: пробы `tcp` / `http`; неисправные бэкенды выводятся и возвращаются автоматически
- Ограничение полосы: `bandwidth_limit` на прокси (например `1MB`) через токен-бакет
- Ограничения ресурсов по пяти измерениям (клиенты, прокси, соединения, очереди), все выведены в метрики
- Белый список портов: `allowPorts` + `maxPortsPerClient`
- Ротация журналов: `log.to` + `log.maxDays`, ежедневное разбиение и очистка
- Хранилище клиента: динамически добавленные прокси переживают перезапуск
- Горячая перезагрузка конфигурации: `log_level` и пароль панели меняются без перезапуска

### Наблюдаемость и управление

- Встроенная веб-панель + Prometheus `/metrics` (включается через `enablePrometheus = true`, по умолчанию выключено) + эндпоинт проверки работоспособности без аутентификации; поддерживается Basic Auth
- Из панели можно добавлять и удалять прокси, отключать клиентов — без правки конфигурации и перезапуска
- Dashboard API v2 (`/api/v2/*`): единый формат ошибок, постраничная выдача, стабильная сортировка; поведение эндпоинтов v1 не изменилось
- Локальный веб-интерфейс / API клиента (`[webServer] port = 7400`): просмотр туннелей / соединений / трафика, а также добавление и удаление прокси
- Профилирование CPU: при `pprofEnable = true` и панель сервера, и локальный веб-интерфейс клиента отдают
  `GET /debug/pprof/profile?seconds=N` (по умолчанию 10 с, максимум 60 с); на Unix возвращается
  protobuf, на Windows — явный 501 (Rust `pprof` требует perf-сигналы / `ucontext_t`)
- SSH-шлюз туннелей (`sshTunnelGateway`): в сервер встроен SSH-сервер, поэтому `ssh -R` из OpenSSH
  может напрямую регистрировать прокси `tcp` / `http` / `https` / `tcpmux` / `stcp`, а плоскость
  данных использует обычные рабочие соединения; если `authorizedKeysFile` не пуст, принимаются только
  ключи из этого файла, а комментарий ключа становится именем пользователя frp
- HTTP-плагины (`httpPlugins`): сервер вызывает внешний HTTP-сервис на событиях
  `Login` / `NewProxy` / `CloseProxy` / `Ping` / `NewWorkConn` / `NewUserConn`, может отклонить запрос
  или переписать данные входа и имя прокси/metas; таймаут 10 с на запрос

### NLink v1: расширение по согласованию (по умолчанию выключено)

Стандартный протокол frp жёстко фиксирует модель транспорта, сессий,
аутентификации и планирования. Некоторые задачи — не случаи «плохой
реализации», а ситуации, когда **в протоколе нет места, чтобы нести
информацию**. Например, миграции соединения нужен идентификатор соединения
на уровне транспорта, а frp надстраивает yamux поверх TCP/TLS, поэтому такого
места нет.

NLink — это слой поверх стандартного протокола frp. Два правила соблюдаются
всегда:

1. **Ни один байт стандартных кадров не меняется** — расширения живут в
   отдельном пространстве имён, официальный frp их никогда не видит;
2. **Не согласовано — значит не существует** — если хоть одна сторона не
   поддерживает, поведение идентично 0.6.x.

**Ни одного дополнительного круга обмена.** Клиент добавляет объявление
возможностей перед первым сообщением протокола (preamble `NFRPLNK1`), а сервер
приписывает подтверждение к `LoginResp._nlink`, который и так отправлял.
Определение опирается только на первый байт: `NFRPLNK1`, `FRP\0\x02\r\n` и `{`
не пересекаются, поэтому ошибки быть не может.

| Возможность | Описание |
|---|---|
| Транспорт QUIC и миграция соединений | Отдельный ALPN `nfrp-nlink`, не смешивается со стандартным QUIC |
| Возобновление сессий | `ConnectionId` уровня процесса не меняется; сервер сохраняет слушатели / порты / маршруты vhost как есть на `resume_ttl` секунд |
| Zero-trust идентификация | Каждое рабочее соединение несёт токен `v1.<exp>.<hmac>`, привязанный к `run_id + user + срок действия` |
| Тонкое ограничение скорости | Токен-бакеты на пару «пользователь × прокси», с поддержкой всплесков |
| Port knocking | Порты по умолчанию невидимы; правильная последовательность открывает порт для этого IP на время |
| Пакетные рабочие соединения | Один `BatchReq` даёт N соединений, убирая круги обмена на каждое |
| Сквозная трассировка | Плоскости управления и данных делят один trace id |

**По умолчанию выключено**, включается на обеих сторонах:

```toml
# frps.toml
[nlink]
enable = true
quic_listen = "0.0.0.0:7000"   # пусто — QUIC не открывается
resume_ttl = 30

# frpc.toml
[nlink]
enable = true
resume = true
quic = true
```

**Сосуществование с официальным frp**: официальный frps не понимает preamble
и отвергает его как заголовок сообщения v1. Клиент перехватывает эту ошибку и
**автоматически возвращается к стандартному режиму, повторяя попытку один
раз**, оставляя в журнале одну строку предупреждения. Туннели продолжают
работать.

| Комбинация | Поведение |
|---|---|
| NFrp × NFrp | Включается по результату согласования |
| NFrp × официальный frp | Возврат к стандартному режиму; функции урезаются, но **связность не страдает** |
| официальный × официальный | Не затрагивается вовсе |

Сборка с `--no-default-features` полностью убирает поля расширения; формат
передачи тогда побайтово совпадает с 0.6.x.

> Схема рукопожатия, кадрирование TLV, способ переноса каждой возможности,
> матрица совместимости и проектные ограничения — на
> [странице NLink сайта документации](https://nu0vo1212.github.io/Rust-Frp/#/nlink).

### Качество инженерии

999 автоматических тестов, включая рукопожатие на реальном стеке QUIC,
сквозную интеграцию и регрессии расшифровки на шифртексте, снятом с
официальных frpc/frps; `cargo audit` не находит ничего; релизные артефакты
сопровождаются `SHA256SUMS` и подписью Ed25519.

Распределение тестов, матрица CI, реальный охват проверки зависимостей,
релизные «ворота» и ручной чек-лист — в **[QUALITY.md](QUALITY.md)**.

## Быстрый старт

### Сборка

```bash
cargo build --release
# Артефакты: <target_directory>/release/nfrp-server (frps), <target_directory>/release/nfrp-client (frpc)
# target_directory определяется `cargo metadata`: если задан CARGO_TARGET_DIR
# или локальный `.cargo/config.toml`, артефакты не в ./target
```

Требуется Rust 1.75+. В Windows используется набор инструментов MSVC.

Можно также скачать релизный пакет; бинарные файлы внутри называются `frps` /
`frpc`, как у официального frp.

### Сервер (публичный хост)

```toml
# frps.toml
bind_addr = "0.0.0.0"
bind_port = 7000
token = "замените на достаточно случайный секрет"

# Необязательно: порт рандеву для настоящего P2P xtcp (откройте UDP)
p2p_port = 7002
```

### Клиент (внутренний хост)

```toml
# frpc.toml
server_addr = "your.server.com"
server_port = 7000
token = "тот же секрет, что на сервере"

[[proxies]]
name = "ssh"
type = "tcp"
local_addr = "127.0.0.1:22"
remote_port = 6000
```

```bash
./nfrp-client -c frpc.toml
```

После этого `your.server.com:6000` ведёт на порт 22 внутреннего хоста.

### Совместимость с официальным frp

NFrp работает на любой стороне официального frp; оба направления проверены
на практике:

| Сервер | Клиент | Статус |
|---|---|---|
| nfrp frps | официальный frpc (tcpMux вкл/выкл, TLS вкл, разные типы прокси) | Пройдено |
| официальный frps | nfrp frpc (tcp_mux вкл/выкл, TLS вкл, разные типы прокси) | Пройдено |
| nfrp frps | официальный frpc (провайдер / посетитель stcp) | Пройдено |

**Маркеры совместимости менять нельзя**: `frpc -v` по-прежнему печатает
просто `0.71.0`, магия протокола и строка версии сохранены, а бинарные файлы
в пакетах по-прежнему называются `frps` / `frpc`. Изменение любого из этих
трёх пунктов сразу ломает совместимость с официальным frp и сторонними
платформами.

## Конфигурация

Ключи конфигурации совпадают с официальным frp, поэтому **исходные
`frps.toml` / `frpc.toml` работают как есть** (поддерживаются camelCase,
двухчастная запись `localIP` + `localPort`, `[metadatas]` и так далее).

Есть два места, где мы **намеренно расходимся** с официальной версией, и оба
важны:

- `local_addr` использует объединённую форму `ip:port` (`127.0.0.1:8080`), а не
  отдельные `localIP` + `localPort`, как в официальном frp. Двухчастная форма
  тоже принимается, но не смешивайте два стиля в одном файле.
- Ротация журналов происходит в **UTC** (в официальной версии — по местному
  времени), потому что сами отметки времени в журналах уже в UTC.

Полностью прокомментированные примеры — в
[`assets/frps.toml`](assets/frps.toml) и
[`assets/frpc.toml`](assets/frpc.toml), либо сгенерируйте их через `--gen-config`.

## Замечания по обновлению

Начиная с 0.5.2 есть несколько **изменений поведения**, которые стоит
проверить до обновления:

| Изменение | Влияние | Что делать |
|---|---|---|
| Панель слушает не loopback и нет `dashboard_user` | Отказ запуска | Задать учётные данные / `bind_addr = "127.0.0.1"` / явно указать `allow_insecure_dashboard = true` |
| Клиентский `[webServer]` слушает не loopback без учётных данных | Отказ запуска | Аварийный переключатель: `allowInsecureRemote = true` |

| Опечатки в ключах `[acl]` | Теперь ошибка (раньше молча игнорировались) | Исправить написание |

Прочее, на что стоит обратить внимание:

- **Для развёртываний с OIDC обязателен TLS.** `privilege_key` в OIDC — это
  исходный access token, он попадает в сообщение входа открытым текстом; любой,
  кто пассивно слушает незашифрованный канал, может его забрать.
- **`transport.tls` на клиенте только шифрует, но не проверяет сертификат
  противоположной стороны** (как и в официальном frp). Это защита от
  пассивного подслушивания, но не от «человека посередине»; если нужно
  защититься от MITM при прямом соединении через публичную сеть, добавьте
  ещё один слой TLS **снаружи**.
- **Стойкость учётных данных входа v1 полностью зависит от token.** С v0.5.7
  сервер **проверяет свежесть отметки времени** (по умолчанию окно ±300 с,
  см. таблицу выше), сокращая возможность повтора с «бесконечно» до «5 минут»;
  но в пределах окна повтор всё ещё возможен, и **стоимость офлайн-перебора
  token не зависит от временного окна** ⇒ для развёртываний в публичной сети
  используйте достаточно случайный token и предпочитайте v2 / OIDC.
- **`user` сообщает сам клиент, сервер не может его проверить.** Без
  `[[roles]]` это просто метка; и **так же остаётся с настроенным `[[roles]]`** —
  любой, у кого есть общий token, может назваться чужим `user` и получить его
  роль. ⇒ `[[roles]]` **не является изоляцией тенантов**, это лишь защита от
  ошибок (с v0.5.7 сервер выводит об этом предупреждение при запуске). Для
  настоящей изоляции используйте OIDC (идентичность берётся из проверенного
  `sub`) либо выдавайте каждому тенанту отдельный token и разворачивайте
  отдельные экземпляры.
- **«Данные минуют сервер» в xtcp не означает «защита от сервера»**: сервер
  хранит `secret_key` и сам генерирует `sid`, поэтому теоретически может
  вычислить секрет P2P. Это защита от **третьих лиц на пути**, а не от самого
  сервера.
- Если не хотите раскрывать внутренние детали, задайте
  `detailed_errors_to_client = false` (по умолчанию `true`, как в официальном
  frp): ошибки клиенту заменяются единым коротким сообщением, что также
  сокращает возможность перечисления имён туннелей stcp/xtcp.
- **Ответы UDP-прокси ограничены** (с v0.5.6): сервер отправляет UDP только на
  те IP посетителей, которые недавно отправляли пакеты на этот порт. Это
  защита от использования frps как UDP-отражателя — обычные клиенты отвечают
  только на адрес, с которого только что получили данные, поэтому **ничего не
  замечают**.
- В примерах конфигурации по умолчанию **нет** прокси; раскомментируйте нужное.
  SSH больше не публикуется по умолчанию.

## Гарантии качества

```bash
cargo fmt --all -- --check                              # форматирование
cargo clippy --workspace --all-targets -- -D warnings   # статический анализ, 0 предупреждений
cargo test --workspace                                  # 999 пройдено / 0 провалено / 13 ignored
```

Все 13 тестов с `#[ignore]` **требуют реального оборудования или прав
администратора** (адаптеры Wintun в Windows, устройства TUN в Linux); это не
сломанные тесты, которые пропустили.

CI запускает те же три проверки на каждый push / PR, плюс полный набор тестов
на трёх операционных системах, кросс-сборку для двух целей musl и
сквозной дымовой тест.

**Подробности в [QUALITY.md](QUALITY.md)**: таблица тестов по целям, матрица
CI, что именно покрывает проверка зависимостей (`cargo audit` / `deny` / `vet`
означают разное), релизные «ворота» и ручной чек-лист.

## Релиз и развёртывание

### Docker

```bash
docker build -t nfrp .
docker run --rm -p 17000:17000 -p 17002:17002/udp \
  -v $PWD/frps.toml:/etc/nfrp/frps.toml nfrp
```

Образ работает от непривилегированного пользователя, использует многоэтапную
сборку musl, а итоговый образ содержит только два бинарных файла и примеры
конфигурации.

### Сборка пакетов самостоятельно

Полные команды упаковки, подписи, кросс-компиляции (включая переменные
окружения Android NDK) и релизных «ворот» — в **[QUALITY.md](QUALITY.md)**.

Кратко: `release.py pack` распаковывает только что собранный пакет и сравнивает
`frps` / `frpc` внутри с исходными артефактами по sha256, завершаясь с ненулевым
кодом при любом расхождении. Этот шаг не является необязательным — реально
бывали релизы, где «имя пакета и версия правильные, а бинарный файл внутри —
от предыдущей версии».

## Текущие ограничения

- **TUN-устройства VirtualNet**: в Linux используется `/dev/net/tun` (нужен root или `CAP_NET_ADMIN`);
  **в Windows используется Wintun** (поддерживается с v0.6.6, требуются права администратора и
  `wintun.dll`, который вы предоставляете сами; в репозитории есть тесты плоскости данных с реальным
  адаптером и двусторонним ping, помеченные `#[ignore]`, которые нужно запускать вручную с правами
  администратора; пути ошибок при отсутствии DLL и при отказе в доступе проверены в сессии без
  повышенных прав, но сама плоскость данных на реальном оборудовании в этом раунде не перепроверялась);
  macOS не реализован — выдаётся явная ошибка, а не тихий отказ
- Соответствие полям конфигурации официальной версии 0.71:

  **Реализовано**: группа TLS-сертификатов (`transport.tls.certFile` / `keyFile` / `trustedCaFile`,
  включая серверный mTLS и клиентские сертификаты), `auth.tokenSource` (файл / внешняя команда,
  клиент и сервер), `includes` (включение конфигураций клиента), `quicBindPort`, `enablePrometheus`,
  `udpPacketSize` (на обеих сторонах; по умолчанию 65507, а не 1500 как в официальной версии — см.
  ниже), клиентские `useEncryption` / `useCompression` (реализованы по официальной golib:
  AES-128-CFB + snappy-поток; проходят модульные тесты и двусторонний обмен в памяти; совместного e2e
  с официальным frpc пока нет), `proxyURL` (исходящий прокси HTTP CONNECT / SOCKS5),
  `dnsServer` (запросы A/AAAA через собственный UDP DNS), `natHoleStunServer` (обнаружение публичного
  отображения по RFC 5389), `pprofEnable` (профиль CPU на Unix, явный 501 на Windows),
  `assetsDir` (каталог статических ресурсов панели), `natholeAnalysisDataReserveHours`
  (срок хранения записей анализа NatHole, 0 — не хранить), `httpPlugins` (серверные обратные вызовы
  входа / прокси / рабочих соединений), `sshTunnelGateway` (SSH-шлюз туннелей для `ssh -R` из OpenSSH).

  **Официальный NatHole / xtcp**: протокол официального контроллера реализован и проверен реальным
  e2e с официальным `frpc 0.71.0` (провайдер и посетитель завершили пробивание UDP-туннеля через
  рабочее соединение `NatHoleSid`, `NatHoleClient` и `NatHoleResp`, доступ прошёл успешно).

  По официальным `pkg/nathole/{classify,analysis}.go` реализованы **полная классификация NAT и выбор
  поведения mode 0–4**: обе стороны EasyNAT — mode 0; одна сторона HardNAT — mode 1 или 2 в
  зависимости от регулярности смены портов; обе стороны HardNAT — mode 3 или 4; ни одна не регулярна —
  возврат к mode 0 «попробовать наудачу». Прогнозирование портов
  (`portsRangeNumber` / `portsRandomNumber`), случайные порты прослушивания (`listenRandomPorts`),
  TTL, `sendDelayMs` / `readTimeoutMs` и все кандидатные адреса STUN также передаются клиенту.

  > В предыдущих версиях этого файла было написано «покрыт только mode 0». Этот вывод относится к
  > версиям до 0.7.2 и недействителен. В 0.7.4 пробел закрыт тестом
  > `mode_选择的六个分支与官方一致`: поломка любой из шести ветвей делает его красным.

  Реальное ограничение сохраняется: откроется ли туннель, зависит от **фактического поведения
  NAT-устройств на обоих концах**. При неудаче в сценариях HardNAT клиент возвращается к ретрансляции
  согласно `fallbackTo` — это предусмотренный путь деградации.

  **Пока не сделано**: e2e-совместимость OIDC с реальным внешним IdP (Keycloak / Azure AD и др.) —
  сейчас девять случаев выполняются против локального mock IdP. У SSH-шлюза для tcpmux / stcp
  проверены только регистрация и очистка; **плоскость данных не имеет e2e**.

  > ~~`webServer.tls.certFile` / `webServer.tls.keyFile` (HTTPS панели) не реализовано~~
  > — **исправление**: HTTPS панели реализован начиная с v0.6.x, есть реальный регрессионный тест
  > HTTPS + HSTS (`server/src/dashboard.rs::web_server_tls_真实_https_和_hsts`). Исходная строка
  > сохранена, чтобы не переписывать историю; текущее состояние определяется этой строкой.

  > Значение по умолчанию `udpPacketSize` **намеренно отличается** от официального: там 1500, а NFrp
  > всегда использовал 65507 (предел протокола UDP). Переход на 1500 **молча обрезал** бы большие
  > UDP-датаграммы у существующих пользователей (пакет приходит, но содержимое усечено) — это гораздо
  > труднее диагностировать, чем ошибку. Если нужно официальное поведение, задайте
  > `udpPacketSize = 1500` явно.
